# P009.1.1 — Application Layer Plan Final Correction & Verification Gate

## 1. Corrections Applied

This document serves as the final, binding implementation plan for Phase P009, correcting and replacing earlier draft plans.

| Item | Problem in Earlier Plans | Final Frozen Correction |
|---|---|---|
| **Game.Reset() & Pending Events** | Risk of undelivered events being cleared or left un-dispatched during `ResetGameAsync`. | `Game.Reset()` itself **MUST NOT** clear `DomainEvents`. At Application level, `ResetGameAsync` explicitly detects pending events, dispatches them via `IDomainEventDispatcher`, calls `game.ClearDomainEvents()` strictly upon success, and only then executes `game.Reset()`. If dispatch fails, reset halts, `ClearDomainEvents()` is NOT called, the exception bubbles up, and the event remains pending for retry. |
| **Concurrency & Synchronization** | Claiming `ConcurrentDictionary` alone makes Game operations thread-safe. | `ConcurrentDictionary` provides thread-safe aggregate lookup/storage, but read-modify-write commands for the same `GameId` must be serialized. An in-memory, per-`GameId` synchronization mechanism (`ConcurrentDictionary<GameId, SemaphoreSlim>` or keyed object lock) is defined to guarantee that concurrent commands against the same `GameId` cannot interleave. |
| **Domain Logic Separation** | Ambiguity over where validations and moves are processed. | Application services orchestrate use cases but **do not implement business rules**. All move legality, current-player checks, win/draw detection, terminal transitions, undo rules, and computer strategies are strictly delegated to `Game` and `WinDetector`. |
| **Canonical Cell Addressing** | Risk of supporting row/col in Application layer. | The entire Application contract uses integer `cellIndex` strictly in the range `0..8`. Zero row/column representations exist in application models or use-case parameters. |
| **DTO Contract Integrity** | Deviating from `docs/06-api-contract.md`. | `GameStateDto`, `MoveDto`, and `ScoreboardDto` strictly reflect the canonical JSON contracts in `docs/06-api-contract.md`. DTOs expose application-safe data only and never leak `Game`, `Board`, `Scoreboard`, or internal domain collections. |
| **Computer Mode Orchestration** | Risk of Application executing strategy rules directly. | Application does not choose cells or evaluate wins. It calls `game.ExecuteTurn(cellIndex, _computerStrategy)` or `game.PlayComputerMove(_computerStrategy)` directly on the aggregate root. |
| **Scoreboard Independence** | Intertwining Game and Scoreboard resets. | `ResetGameAsync` MUST NOT reset or modify scoreboard counters. `ResetScoreboardAsync` MUST NOT modify any `Game` aggregate. |
| **Event Dispatch Ordering** | Ambiguous failure boundaries. | Explicit lifecycle: Load $\rightarrow$ Domain operation $\rightarrow$ retrieve pending events $\rightarrow$ dispatch $\rightarrow$ clear events ONLY on success $\rightarrow$ persist aggregate $\rightarrow$ return DTO. |
| **Repository Ownership** | Interface placed in Application layer. | `IGameRepository` belongs to `TicTacToe.Domain.Repositories`. `InMemoryGameRepository` belongs to `TicTacToe.Infrastructure.Repositories`. The Application layer has zero references to Infrastructure. |

### 3.2 Implementation (`TicTacToe.Infrastructure.Repositories.InMemoryGameRepository`)
- Uses `ConcurrentDictionary<GameId, Game>` for thread-safe aggregate lookup and storage.
- Stores authoritative, live `Game` aggregate references. Aggregates are NOT cloned or detached.
- If an aggregate is not found, `GetByIdAsync` returns `null`.
- Single-instance in-memory storage suitable for the local assessment lifecycle.

## 4. Final Event Lifecycle & Reset Semantics

### 4.1 Mutating Use Cases (`MakeMoveAsync`)
1. Obtain per-`GameId` synchronization lock.
2. Retrieve authoritative `Game` aggregate via `_gameRepository.GetByIdAsync(gameId)`.
   - If `null` $\rightarrow$ throw `GameNotFoundException(gameId)`.
3. Invoke domain operation:
   - Two-Player: `game.MakeMove(player, cellIndex);`
   - Computer Mode: `game.ExecuteTurn(cellIndex, _computerStrategy);`
4. Inspect `game.DomainEvents`.
   - If events exist:
     - Dispatch via `await _eventDispatcher.DispatchAsync(game.DomainEvents);`
     - Upon successful completion: `game.ClearDomainEvents();`
     - If dispatch throws: do NOT clear events; exception bubbles up to caller; event remains pending on aggregate for retry.
5. Persist aggregate state: `await _gameRepository.SaveAsync(game);`
6. Query session scoreboard: `var scoreboard = await _scoreboardRepository.GetScoreboardAsync();`
7. Release lock and return `game.ToDto(scoreboard)`.

### 4.2 Reset Use Case (`ResetGameAsync`)
1. Obtain per-`GameId` synchronization lock.
2. Retrieve authoritative `Game` aggregate via `_gameRepository.GetByIdAsync(gameId)`.
   - If `null` $\rightarrow$ throw `GameNotFoundException(gameId)`.
3. Drain pending events first:
   - If `game.DomainEvents.Count > 0`:
     - Dispatch: `await _eventDispatcher.DispatchAsync(game.DomainEvents);`
     - Upon success: `game.ClearDomainEvents();`
     - If dispatch throws: halt reset, do NOT call `ClearDomainEvents()`, propagate exception.
4. Execute `game.Reset();`.
   - Preserves `game.Id` (FR-12).
   - Reinitializes board, player to X, status to `InProgress`, clears moves and undo stack.
   - Does NOT emit domain events.
   - Does NOT touch or mutate Scoreboard.
5. Persist reset aggregate: `await _gameRepository.SaveAsync(game);`
6. Query session scoreboard: `var scoreboard = await _scoreboardRepository.GetScoreboardAsync();`
7. Release lock and return `game.ToDto(scoreboard)`.

### 4.3 Scoreboard Reset Use Case (`ResetScoreboardAsync`)
1. Retrieve session `Scoreboard` via `_scoreboardRepository.GetScoreboardAsync()`.
2. Invoke `scoreboard.Reset();`.
   - Resets `XWins = 0, OWins = 0, Draws = 0, TotalGames = 0`.
   - Preserves `_processedEventIds` to prevent duplicate counting of historical events.
3. Persist: `await _scoreboardRepository.SaveScoreboardAsync(scoreboard);`
4. Return `scoreboard.ToDto()`.
5. Does NOT mutate or touch any `Game` aggregate.

## 5. Final Concurrency Model

**Architectural Rule**:
> "ConcurrentDictionary provides thread-safe aggregate lookup/storage, but read-modify-write commands for the same GameId must be serialized."

### Per-`GameId` Synchronization:
In `GameService`, an in-memory key-locking mechanism (`ConcurrentDictionary<GameId, SemaphoreSlim>`) serializes commands targeting the same `GameId`:
```csharp
var semaphore = _gameLocks.GetOrAdd(gameId, _ => new SemaphoreSlim(1, 1));
await semaphore.WaitAsync(cancellationToken);
try
{
    // Load -> Mutate -> Dispatch -> Clear -> Save
}
finally
{
    semaphore.Release();
}
```
This guarantees:
- Two concurrent moves on the same game cannot execute simultaneously or corrupt turn alternation.
- Undo and Move cannot race on the same game.
- Move and Reset cannot race on the same game.
- Moves on *different* `GameId`s proceed fully concurrently without contention.
- No distributed locking or database concurrency tokens required for this in-memory single-process architecture.
