4. Invoke Domain behavior.

# 9. DOMAIN EVENT LIFECYCLE

For every mutating game operation:

1. Load aggregate.
2. Execute domain operation.
3. Check `game.DomainEvents`.
4. Dispatch pending events.
5. If dispatch succeeds:

   ```csharp
   game.ClearDomainEvents();
   ```
6. Persist aggregate.

If dispatch fails:

* propagate the exception
* DO NOT clear DomainEvents
* DO NOT silently continue
* preserve the pending event for retry

For `ResetGameAsync`:

1. Load Game.
2. If pending DomainEvents exist:

   * dispatch them
   * clear only after successful dispatch
3. Execute `game.Reset()`
4. Persist reset aggregate

If dispatch fails:

* DO NOT reset the game
* DO NOT clear the event
* propagate the failure

`Game.Reset()` itself MUST NOT clear DomainEvents.

---

# 10. IMPORTANT FAILURE SEMANTICS

Document explicitly that the current architecture is an in-memory single-process assessment architecture.

Do not claim distributed transaction guarantees.

If persistence fails after successful event dispatch, the exception must propagate.

Do not silently swallow persistence failures.

Do not introduce a fake transaction abstraction merely to hide this limitation.

Document the limitation clearly in the P009 review.

---

# 11. PER-GAME CONCURRENCY

`GameService` MUST serialize mutating operations for the same GameId.

Use:

```csharp
ConcurrentDictionary<GameId, SemaphoreSlim>
```

Requirements:

* same GameId → serialized
* different GameIds → may execute concurrently
* cancellation-aware `WaitAsync`
* semaphore released in `finally`

This protects:

* CurrentPlayer
* Board
* MoveHistory
* Undo stack
* Status
* Winner
* WinningCells
* DomainEvents

Document that this is:

* single-process synchronization
* NOT distributed locking
* NOT optimistic concurrency
* NOT database locking

Lock lifetime may be process lifetime because games themselves are stored in the in-memory repository.

Document this as an explicit assessment limitation.
