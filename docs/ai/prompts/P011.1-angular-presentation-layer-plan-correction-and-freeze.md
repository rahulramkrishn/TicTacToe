# P011.1 — Angular Presentation Layer Plan Correction & Freeze

## Objective

Apply corrections to the P011.0 Angular Presentation Layer plan and freeze the architectural specification prior to code implementation in P011.2.

This is a **PLAN CORRECTION & VERIFICATION GATE ONLY**.
Do NOT write application code, HTML templates, or Angular components in this phase.

---

## 1. Architectural Boundary & Invariants

```text
Angular UI (Presentation Layer)
    │
    │ HTTP only (Typed JSON / RFC 7807 ProblemDetails)
    ▼
REST API (TicTacToe.Api — P010.2)
    │
    ▼
Application Layer (TicTacToe.Application — P009)
    │
    ▼
Domain Layer (TicTacToe.Domain — P001–P008)
```

The frontend is strictly a **dumb presentation adapter and reactive consumer**:
1. **Zero Business Rules in Frontend**:
   - Win detection is strictly performed server-side.
   - Draw detection is strictly performed server-side.
   - Computer strategy is strictly executed server-side.
   - Undo memento restoration is strictly executed server-side.
   - Scoreboard counter updates are strictly triggered server-side.
2. **Authoritative State Consumption**:
   - The UI purely renders authoritative `GameStateDto` and `ScoreboardDto` received over HTTP.
3. **Canonical Cell Addressing**:
   - The frontend communicates solely in `cellIndex` (`0..8`).
   - Coordinate conversions (`row`, `column`) exist purely for user presentation in the move history log and cell accessibility labels.

---

## 2. Frozen Review Corrections

1. **Atomic Computer Mode API Semantics**:
   - One UI click → one HTTP request (`POST /api/games/{id}/moves` with `player: 'X'` and `cellIndex`).
   - Backend returns complete authoritative state after the human X + computer O turn pair.
   - The frontend never calls the API separately for the computer move.
2. **RFC 7807 ProblemDetails Error Model**:
   - Model `ProblemDetails` with all 7 fields: `type`, `title`, `status`, `code`, `detail`, `instance`, `traceId`.
   - The facade retains and exposes complete error details; it does not reduce them to generic messages.
3. **Operation-Safe In-Flight Loading Guards**:
   - All interactive controls (board cells, Undo, Reset, New Game) disabled while a request is in-flight.
   - Duplicate HTTP calls dropped at the facade.
   - Loading state restored in `finalize()` for both success and failure.
4. **Initialization Failure Handling**:
   - If `initGame()` or `newGame()` fails, no fake/default game is rendered. An error alert with a retry action is displayed.
5. **Authoritative Scoreboard Synchronization**:
   - Scoreboard values are hydrated directly from `GameStateDto.scoreboard` or `/api/scoreboard`. Never calculated locally.
6. **Explicit Reset Semantics**:
   - `resetGame()` calls `POST /api/games/{id}/reset`, preserving the existing `gameId`.
7. **Explicit New Game Semantics**:
   - `newGame(mode)` calls `POST /api/games`, creating a new session with a new `gameId`.
8. **Testable Accessibility Requirements**:
   - Semantic `<button>` elements for all cells.
   - Dynamic ARIA labels reflecting cell state (`"Cell 5, row 2 column 2, empty"`).
   - Disabled attributes on occupied cells and during in-flight operations.
   - High-contrast visible focus rings.
   - Live region (`aria-live="polite"`) for turn, win, and draw announcements.
