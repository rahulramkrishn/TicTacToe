# P009.1 — Application Layer Plan Correction & Verification

## Purpose

P009.0 produced the initial plan for implementing the TicTacToe Application layer.

Before implementing any P009 code, perform a strict architectural review of the P009.0 plan against the complete repository specification and all previously implemented phases.

This phase is a **PLAN CORRECTION AND VERIFICATION ONLY** phase.

Do NOT implement application code.
Do NOT create controllers.
Do NOT create DTOs.
Do NOT create Angular UI.
Do NOT add persistence.
Do NOT modify the Domain model unless the review discovers a documented specification contradiction that must be escalated.

The objective is to produce a corrected, implementation-ready P009 plan.

# 3. P009 Responsibility

Determine precisely what P009 is supposed to implement.

P009 must establish the Application-layer use-case orchestration required before the HTTP API layer is implemented.

The Application layer must:

- orchestrate use cases;
- coordinate Domain aggregates;
- coordinate repositories;
- coordinate domain-event dispatch;
- expose application-level contracts/interfaces where appropriate;
- translate application concerns without leaking HTTP concerns into Domain/Application;
- preserve Domain invariants;
- remain independent of ASP.NET Core;
- remain independent of Angular;
- avoid embedding business rules that belong to Domain;
- provide deterministic, testable use-case behavior.

The Application layer must NOT:

- contain HTTP controllers;
- contain ASP.NET Core action results;
- know about HTTP status codes;
- contain Angular-specific concepts;
- directly manipulate private Domain state;
- duplicate win/draw rules;
- duplicate computer strategy rules;
- duplicate undo rules;
- directly update Scoreboard outside the established domain-event mechanism;
- introduce EF Core;
- introduce SQL;
- introduce external messaging infrastructure.

# 5. Application Use Cases

The corrected P009 plan must explicitly identify the application use cases required by the specification.

At minimum evaluate the need for:

### Create Game

Responsible for creating a new Game aggregate.

Must not contain game-rule logic.

### Get Game

Responsible for retrieving the authoritative Game aggregate/state.

### Make Human Move

Responsible for:

1. loading the game;
2. invoking the Domain aggregate;
3. handling Computer Mode orchestration through the Domain API already established;
4. dispatching pending domain events after successful domain execution;
5. persisting the resulting aggregate state where applicable;
6. returning an application result.

### Undo

Responsible for invoking the Domain `Undo()` operation.

Do not reimplement Memento behavior in Application.

### Reset

Responsible for invoking `Game.Reset()`.

Respect the frozen rule that:

```text
Reset preserves gameId.
```

Also preserve the established domain-event lifecycle.

### Get Scoreboard

Responsible for obtaining the authoritative Scoreboard through its repository.

Do not create a second scoreboard instance.

# 6. Domain Event Dispatch Lifecycle

This is a critical architectural requirement.

The corrected P009 plan MUST explicitly preserve:

```text
Application Use Case
       |
       v
Load Game
       |
       v
Game Domain Operation
       |
       +---- terminal transition
       |          |
       |          v
       |    GameCompletedEvent
       |
       v
Persist/retain aggregate state
       |
       v
Dispatch pending DomainEvents
       |
       v
GameCompletedEventHandler
       |
       v
Scoreboard
       |
       v
ClearDomainEvents ONLY after successful dispatch
```

The plan must define what happens if dispatch fails.

Required behavior:

```text
Dispatch fails
    |
    v
Exception propagates
    |
    v
DomainEvents remain pending
    |
    v
Caller can retry
```

Do not introduce silent event loss.

# 7. Repository Boundaries

Review the existing repository interfaces.

The Application layer should depend on abstractions rather than Infrastructure implementations.

The corrected plan must clearly define:

```text
Application
    |
    +--> IGameRepository
    |
    +--> IScoreboardRepository
    |
    +--> IDomainEventDispatcher
```

Infrastructure provides implementations.

Do not introduce unnecessary repository abstractions if existing interfaces already satisfy the requirement.

Do not allow:

```text
Application --> Infrastructure concrete class
```

unless there is a documented architectural reason.

---

# 8. Game Repository Semantics

Pay particular attention to the fact that the current system is in-memory.

The corrected plan must determine and document:

* how Game instances are stored;
* whether the same aggregate instance or detached instances are used;
* how concurrent access is handled;
* how `GameId` is used;
* what happens when a game does not exist;
* whether repository methods are synchronous or asynchronous;
* why that choice is appropriate for the current in-memory implementation.

Do not introduce artificial asynchronous behavior merely because the eventual database implementation may be asynchronous.

If async interfaces are proposed, document the architectural reason.

---

# 9. Scoreboard Repository Semantics

Verify that the Application layer uses the existing authoritative scoreboard repository.

The Application layer must not:

* instantiate a new Scoreboard per request;
* maintain scoreboard counters itself;
* update scoreboard counters directly;
* bypass `GameCompletedEventHandler`.

The intended relationship is:

```text
Game
 |
 | GameCompletedEvent
 v
Application Dispatcher
 |
 v
GameCompletedEventHandler
 |
 v
IScoreboardRepository
 |
 v
Authoritative Scoreboard
```

# 10. Error Handling

The corrected P009 plan must define application-level error behavior without introducing HTTP concepts.

Review how Domain exceptions are surfaced.

Examples include:

* game not found;
* invalid turn;
* occupied cell;
* completed game;
* cannot undo;
* invalid operation for game mode;
* invalid strategy invocation.

Do not convert these into HTTP status codes in Application.

HTTP translation belongs to the later API phase.

Application results/exceptions must remain transport-neutral.

# 12. Transaction / Consistency Analysis

The corrected plan must explicitly reason about consistency between:

```text
Game state
DomainEvents
Scoreboard
```

Because the current implementation is in-memory and synchronous, document the consistency model.

At minimum explain:

* when Game state becomes authoritative;
* when domain events are dispatched;
* when Scoreboard changes;
* what happens if event handling fails;
* how retry works;
* how duplicate event delivery is handled;
* why Scoreboard idempotency remains necessary.

Do not introduce a distributed transaction.

Do not introduce a message broker.

Do not introduce an outbox unless the existing requirements explicitly demand it.

# 14. Dependency Direction

The corrected P009 plan must preserve:

```text
TicTacToe.Domain
        ^
        |
TicTacToe.Application
        ^
        |
TicTacToe.Infrastructure
        ^
        |
TicTacToe.Api
```

More precisely, Infrastructure may implement Application abstractions, while API consumes Application services.

The plan must prevent:

```text
Domain --> Application
Domain --> Infrastructure
Domain --> API
Application --> API
Application --> Angular
```

# 15. Testing Plan

The corrected P009 plan must contain a comprehensive Application-layer test strategy.

Tests should verify at minimum:

### Create Game

* creates game;
* valid initial state;
* unique game IDs where required.

### Get Game

* existing game retrieval;
* missing game behavior.

### Human Move

* delegates to Domain;
* valid move succeeds;
* invalid move surfaces correctly;
* turn behavior remains Domain-owned.

### Computer Mode

* Application does not implement strategy;
* Domain orchestrates human/computer logical turn;
* terminal human move does not invoke computer move;
* events are dispatched correctly.

### Undo

* delegates to Domain Memento behavior;
* terminal undo restrictions remain intact.

### Reset

* delegates to Domain;
* preserves GameId;
* clears appropriate play state;
* does not silently discard pending domain events.

### Domain Events

* successful dispatch clears pending events;
* failed dispatch retains events;
* GameCompletedEvent is dispatched exactly once successfully;
* retry is possible.

### Scoreboard

* Application retrieves authoritative scoreboard;
* scoreboard changes only through event handler;
* duplicate events remain idempotent.

### Boundary Tests

Verify that Application has no dependency on:

* ASP.NET Core;
* Angular;
* EF Core;
* Infrastructure concrete classes where abstraction is required.
