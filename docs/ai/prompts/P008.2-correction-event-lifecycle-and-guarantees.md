# P008.2 — Correct P008 Event Lifecycle, Exactly-Once Guarantees & Concurrency

## Purpose

The revised P008 implementation plan is broadly approved, but three architectural issues must be corrected before implementation:

1. `Game.Reset()` currently contradicts the event lifecycle specification.
2. "Exactly-once business effect" is too strong for the in-memory architecture.
3. Scoreboard concurrency/idempotency semantics need to be explicitly defined.

This is a **planning correction only**.

# 2. Reconcile Game.Reset() and DomainEvents

The current plan contains a contradiction.

It states that:

```text
Game.Reset() must NOT silently discard an undelivered GameCompleted event
```

but also says:

```text
Game.Reset() clears _domainEvents
```

These statements must be reconciled.

## Required architectural decision

Adopt this rule:

```text
Game.Reset()
    MUST NOT clear DomainEvents.
```

The Game aggregate is responsible for:

```text
creating domain events
retaining pending domain events
exposing pending domain events
```

The Application layer is responsible for:

```text
retrieving pending events
dispatching them
clearing them only after successful dispatch
```

Therefore the lifecycle becomes:

```text
Game.MakeMove()
      ↓
terminal transition
      ↓
GameCompletedEvent created
      ↓
Game.DomainEvents contains event
      ↓
Application retrieves event
      ↓
Application dispatches event
      ↓
handler succeeds
      ↓
Application calls ClearDomainEvents()
      ↓
Game.Reset()
```

A reset must never silently destroy an event that has not yet been successfully dispatched.

# 3. Reset While an Event Is Pending

Explicitly define what happens if:

```text
Game.DomainEvents.Count > 0
```

when `Reset()` is requested.

The plan must choose one explicit behavior.

Preferred decision:

```text
Game.Reset()
```

does not clear events.

The application/use-case layer must ensure pending events are dispatched before reset is allowed.

If the existing requirements make this impossible, document the alternative explicitly rather than silently clearing events.

Do NOT allow:

```text
pending GameCompletedEvent
        ↓
Game.Reset()
        ↓
event silently disappears
```

# 4. Correct Exactly-Once Terminology

Replace the current claim:

```text
Exactly-Once Business Effect — Guaranteed (In-Process)
```

with more precise guarantees.

The architecture should state:

```text
Exactly-once event generation
    = guaranteed within the Game aggregate lifecycle.

Idempotent event handling
    = guaranteed for duplicate delivery of the same EventId.

At-most-once scoreboard mutation per EventId
    = guaranteed by Scoreboard idempotency.

Durable exactly-once processing
    = NOT guaranteed.

Distributed exactly-once delivery
    = NOT claimed.
```

The plan must explicitly explain why:

```text
in-memory application
+
no durable outbox
+
no distributed transaction
+
no durable event store
```

means distributed/durable exactly-once semantics cannot be claimed.

This is an important architectural distinction.

# 5. Scoreboard Idempotency Under Concurrency

Review the current design:

```text
Scoreboard
    _processedEventIds
    XWins
    OWins
    Draws
```

The operation:

```text
RecordGameCompleted(event)
```

must be conceptually atomic:

```text
check EventId
     ↓
if already processed
     ↓
return false
     ↓
otherwise record EventId
     ↓
increment appropriate counter
     ↓
return true
```

Ensure that the design cannot produce:

```text
same EventId
    ↓
two concurrent handlers
    ↓
two counter increments
```

Do not introduce distributed locks.

Do not introduce a database.

Do not introduce a message broker.

Keep the solution appropriate for the in-memory assessment architecture.

# 6. Repository Concurrency

Review:

```text
InMemoryScoreboardRepository
```

The plan currently states that it is thread-safe.

Make the design precise.

If the repository exposes:

```text
GetScoreboardAsync()
SaveScoreboardAsync()
```

explain how concurrent event handling remains safe.

Prefer a single authoritative in-memory Scoreboard instance for the session where appropriate.

Avoid a design where:

```text
Get
 ↓
detached Scoreboard copy
 ↓
modify
 ↓
Save
```

can cause lost updates.

If the repository returns the authoritative aggregate instance, document that decision.

If it returns a copy, define the synchronization mechanism required to preserve atomicity.

Choose the simplest correct solution.

---

# 7. Scoreboard Reset and Concurrency

Preserve the frozen rule:

```text
Scoreboard.Reset()
    resets counters
    preserves processed EventIds
```

Ensure that `Reset()` and `RecordGameCompleted()` cannot produce inconsistent state if they are invoked concurrently.

Do not over-engineer this.

The goal is to demonstrate awareness of aggregate concurrency boundaries, not to build a distributed system.

# 10. Event Clearing Ownership

Make this boundary explicit:

```text
Game
    creates events
    stores events
    exposes events

Application
    dispatches events
    determines successful dispatch
    clears events after success

Scoreboard
    applies completion event idempotently

Infrastructure
    provides concrete in-memory storage where required
```

The Game aggregate must not:

```text
dispatch events
call handlers
know Scoreboard
clear its own events automatically after creation
```
