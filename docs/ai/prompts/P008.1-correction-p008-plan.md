# 4. Correction #1 — Exactly-Once Semantics

The revised plan MUST explicitly distinguish the following three concepts.

## A. Exactly-once event generation

A single terminal transition:

```text
InProgress → Won
```

or:

```text
InProgress → Draw
```

must create exactly one `GameCompleted` domain event.

Examples:

```text
X winning move
    → one GameCompleted event

O winning move
    → one GameCompleted event

draw-producing move
    → one GameCompleted event
```

Repeated calls after completion are rejected and must not create another completion event.

---

## B. Idempotent event handling

The scoreboard must safely handle accidental duplicate delivery of the same event.

Example:

```text
GameCompleted(EventId = E1)
GameCompleted(EventId = E1)
```

must result in:

```text
scoreboard updated once
```

not twice.

---

## C. Exactly-once business effect

Use precise language.

P008 is an in-process/in-memory assessment architecture.

Therefore DO NOT claim:

```text
distributed exactly-once delivery
```

or:

```text
distributed exactly-once processing
```

There is no durable event broker, transaction coordinator, or distributed event store.

The correct architectural statement should be equivalent to:

```text
P008 guarantees exactly-once terminal event generation
within the Game aggregate lifecycle and provides idempotent
scoreboard application for duplicate delivery of the same event
within the scoreboard lifecycle.
```

Clearly document the scope and limitations.

This distinction must appear in:

* P008 plan
* P008 review
* architecture traceability where appropriate
* ADR-007 implementation notes if applicable

# 5. Correction #2 — Scoreboard Idempotency and Reset

The initial plan proposed maintaining processed `EventId` values for duplicate protection.

It also proposed that `Scoreboard.Reset()` clears this processed-event state.

These decisions must be reconciled.

## Required decision

Use the following behavior unless the existing specification explicitly proves another behavior is required:

```text
Scoreboard.Reset()
    ↓
X wins = 0
O wins = 0
Draws = 0
    ↓
processed-event identity information remains intact
```

The purpose is:

```text
Reset counters
≠
forget previously processed events
```

Therefore:

```text
Event E1 processed
    ↓
X wins = 1

Scoreboard.Reset()
    ↓
X wins = 0

E1 delivered again
    ↓
must NOT increment X wins
```

Explain this decision in the revised plan.

Do NOT introduce unnecessary scoreboard epochs/generations unless the existing requirements demand them.

# 6. Correction #3 — Domain Event Lifecycle

Explicitly define the complete lifecycle of a domain event.

The revised plan must answer all of these questions:

```text
Who creates GameCompleted?
Who stores it?
Who exposes it?
Who retrieves it?
Who dispatches it?
Who handles it?
When is it considered dispatched?
When is it cleared?
What happens if Game.Reset() occurs?
```

The preferred conceptual lifecycle is:

```text
Application command
      ↓
Game.MakeMove / ExecuteTurn
      ↓
Game reaches terminal state
      ↓
Game creates GameCompleted
      ↓
Game stores event in DomainEvents
      ↓
Application retrieves pending events
      ↓
Application dispatches event
      ↓
GameCompleted handler processes event
      ↓
Scoreboard updated
      ↓
Successfully dispatched event is cleared
```

The important rule is:

```text
Game.Reset() MUST NOT be responsible for discarding
an undelivered GameCompleted event.
```

Do not design Reset so that it can silently destroy a pending completion event before the application has had an opportunity to dispatch it.

If the actual architecture requires a different lifecycle, explain it explicitly and justify it against the existing code and documents.

# 7. Correction #4 — Game Reset vs Event Lifecycle

The frozen decision is:

```text
Reset Game
    → same gameId
```

P008 must explicitly define:

```text
Game.Reset()
    → resets game state
    → resets board
    → resets move history
    → resets Memento state as specified by P006
    → resets status/current player as specified
    → does NOT update scoreboard
    → does NOT create GameCompleted
    → does NOT re-count previous completion
```

Also analyze the case where a completion event is pending.

The revised plan must explain how the application boundary guarantees that a valid completion event is not lost.

# 10. Correction #7 — GameCompleted Event Payload

Freeze the event payload deliberately.

The revised plan must specify the exact fields.

The preferred shape is conceptually:

```text
GameCompleted
├── EventId
├── GameId
├── Result
├── Winner
├── WinningCells
└── MoveCount
```

But verify every field against the actual specification before committing to it.

Rules:

```text
Result = Won | Draw

Winner = X | O
```

for a win, and:

```text
Winner = null
```

for a draw.

For a draw:

```text
WinningCells = empty
```

For a win:

```text
WinningCells = exactly the canonical winning 3 cells
```

The event must be immutable.

The event must represent the completion fact at the time of completion.

The scoreboard handler should NOT need to retrieve the Game aggregate to understand the completion result.

Avoid:

```text
Scoreboard
   ↓
GameRepository
   ↓
Game
```

merely to process a completion event.
