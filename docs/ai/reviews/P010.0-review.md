# P010.0 Review — API/Web Architecture & Contract Plan

## 1. Executive Summary

Phase **P010** will establish the HTTP REST API layer (`TicTacToe.Api`) as the external transport adapter for the Tic-Tac-Toe system.

This document presents the comprehensive, Principal-level **P010.0 Architecture & Contract Plan** produced prior to writing any API implementation code. It reconciles the primary API contract ([`docs/06-api-contract.md`](file:///c:/Labs/TicTacToe/docs/06-api-contract.md)), all Non-Functional Requirements ([`docs/03-nfr.md`](file:///c:/Labs/TicTacToe/docs/03-nfr.md)), and frozen architectural decisions with the already implemented and verified Domain (`TicTacToe.Domain`, P004–P008) and Application (`TicTacToe.Application`, P009) layers.

**Key Architectural Commitments for P010:**
1. **Thin Controllers**: Controllers contain zero business rules, zero win/draw calculations, zero turn alternations, and zero computer strategy logic. They strictly translate HTTP requests to application commands and application DTOs to HTTP responses.
2. **Strict Inward Dependencies**: `TicTacToe.Api` references `TicTacToe.Application` and `TicTacToe.Infrastructure` (solely for DI composition in `Program.cs`). `TicTacToe.Application` and `TicTacToe.Domain` remain completely decoupled from ASP.NET Core and HTTP concepts.
3. **Canonical Cell Addressing**: All endpoints strictly use `cellIndex: 0..8`. Row/column addressing is rejected.
4. **Identity & State Reset**: `POST /api/games/{gameId}/reset` preserves the existing `gameId` while returning fresh play state and preserving the session scoreboard.
5. **Deterministic Error Handling**: Standard RFC 7807 `ProblemDetails` error payload with structured error codes (`GAME_NOT_FOUND`, `INVALID_CELL_INDEX`, `CELL_OCCUPIED`, `INVALID_TURN`, `GAME_ALREADY_COMPLETED`, `CANNOT_UNDO`).
6. **Concurrency Preservation**: `GameService` registered as **Singleton** to ensure the encapsulated per-`GameId` `SemaphoreSlim` instances serialize concurrent HTTP requests targeting the same game across ASP.NET Core worker threads.

## 4. API Contract Summary & Endpoint Catalog

All routes reside under the `/api/` prefix.

| HTTP Method | Route | Controller | Action | Success Status | Error Status Codes | Description |
|---|---|---|---|---|---|---|
| `POST` | `/api/games` | `GamesController` | `CreateGame` | `201 Created` | `400 Bad Request` | Initializes new game session; returns `GameStateDto` with `Location` header. |
| `GET` | `/api/games/{gameId}` | `GamesController` | `GetGame` | `200 OK` | `404 Not Found` | Retrieves authoritative state without side effects. |
| `POST` | `/api/games/{gameId}/moves` | `GamesController` | `MakeMove` | `200 OK` | `400 Bad Request`, `404 Not Found`, `409 Conflict` | Applies player move; in Computer mode executes computer response; returns updated state. |
| `POST` | `/api/games/{gameId}/undo` | `GamesController` | `Undo` | `200 OK` | `404 Not Found`, `409 Conflict` | Reverts 1 move (TwoPlayer) or 2 moves (Computer); returns updated state. |
| `POST` | `/api/games/{gameId}/reset` | `GamesController` | `ResetGame` | `200 OK` | `404 Not Found` | Resets board/turns under **same `gameId`**; drains pending events; preserves scoreboard. |
| `GET` | `/api/scoreboard` | `ScoreboardController`| `GetScoreboard` | `200 OK` | None | Returns session scoreboard counters without side effects. |
| `POST` | `/api/scoreboard/reset`| `ScoreboardController`| `ResetScoreboard`| `200 OK` | None | Clears scoreboard counters; preserves deduplication cache; does not alter active games. |

## 5. Request & Response DTO Design

### 5.1 Request Contracts
1. **Create Game Request** (`CreateGameRequest.cs`):
   ```csharp
   public sealed record CreateGameRequest(
       GameMode Mode = GameMode.TwoPlayer);
   ```
2. **Make Move Request** (`MakeMoveRequest.cs`):
   ```csharp
   public sealed record MakeMoveRequest(
       Player Player,
       int CellIndex);
   ```
   - Matches `docs/06-api-contract.md` §9 verbatim.
   - `cellIndex` strictly required in range `0..8`.
   - Rejects `row` and `column`.

### 5.2 Response Contracts (from `TicTacToe.Application.Models`)
1. **`GameStateDto`**:
   - `Guid GameId`: Unique identifier of the game.
   - `IReadOnlyList<Player?> Board`: Array of 9 nullable Player values (`"X"`, `"O"`, or `null`).
   - `Player CurrentPlayer`: Current player whose turn it is (`"X"` or `"O"`).
   - `GameMode Mode`: Game mode (`"TwoPlayer"` or `"Computer"`).
   - `GameStatus Status`: Game status (`"InProgress"`, `"Won"`, or `"Draw"`).
   - `Player? Winner`: Winner if won; otherwise `null`.
   - `IReadOnlyList<int> WinningCells`: Indices of winning cells if won; otherwise empty array.
   - `IReadOnlyList<MoveDto> MoveHistory`: Chronological list of moves executed.
   - `bool CanUndo`: Boolean indicating if undo is currently permitted.
   - `ScoreboardDto Scoreboard`: Session scoreboard counters.
2. **`MoveDto`**:
   - `int MoveNumber`: 1-based move sequence number.
   - `Player Player`: Player who made the move.
   - `int CellIndex`: Cell index in `0..8`.
3. **`ScoreboardDto`**:
   - `int XWins`, `int OWins`, `int Draws`, `int TotalGames`.

## 6. HTTP Status Code Strategy & Error Mapping

All error responses use RFC 7807 `ProblemDetails` with `Content-Type: application/problem+json`.

```json
{
  "type": "https://tools.ietf.org/html/rfc7231#section-6.5.8",
  "title": "Invalid move",
  "status": 409,
  "detail": "Cell 4 is already occupied.",
  "code": "CELL_OCCUPIED",
  "traceId": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01"
}
```

### Exception to HTTP Status Mapping Matrix

| Exception Type | Layer | HTTP Status | Code String | Title | Client Message / Detail |
|---|---|---|---|---|---|
| `GameNotFoundException` | Application | `404 Not Found` | `GAME_NOT_FOUND` | `Game Not Found` | `Game with ID '{gameId}' was not found.` |
| `InvalidCellIndexException`| Domain | `400 Bad Request` | `INVALID_CELL_INDEX` | `Invalid Cell Index` | `Cell index must be between 0 and 8.` |
| `CellOccupiedException` | Domain | `409 Conflict` | `CELL_OCCUPIED` | `Cell Occupied` | `Cell {cellIndex} is already occupied.` |
| `InvalidTurnException` | Domain | `409 Conflict` | `INVALID_TURN` | `Invalid Turn` | `It is not player {player}'s turn.` |
| `GameAlreadyCompletedException` | Domain | `409 Conflict` | `GAME_ALREADY_COMPLETED` | `Game Already Completed` | `Cannot make a move in a completed game.` |
| `CannotUndoException` | Domain | `409 Conflict` | `CANNOT_UNDO` | `Cannot Undo Move` | `Undo operation is not available.` |

| All other unhandled exceptions | Any | `500 Internal Server Error` | `INTERNAL_SERVER_ERROR` | `Internal Server Error` | `An unexpected error occurred. Please try again later.` |

| Validation Concern | Layer Owning Validation | Handling Mechanism | HTTP Result |
|---|---|---|---|

## 8. Dependency Injection & Lifetime Plan

All services will be configured in `TicTacToe.Api/Program.cs`:

```csharp
// Repositories (Authoritative in-memory state)
builder.Services.AddSingleton<IGameRepository, InMemoryGameRepository>();
builder.Services.AddSingleton<IScoreboardRepository, InMemoryScoreboardRepository>();

// Domain Services & Strategies
builder.Services.AddSingleton<IComputerMoveStrategy, BasicComputerMoveStrategy>();

// Domain Event Infrastructure
builder.Services.AddSingleton<IDomainEventDispatcher>(sp =>
{
    var dispatcher = new DomainEventDispatcher();
    var scoreboardRepo = sp.GetRequiredService<IScoreboardRepository>();
    dispatcher.RegisterHandler(new GameCompletedEventHandler(scoreboardRepo));
    return dispatcher;
});

// Application Services
// CRITICAL: Registered as Singleton so the internal ConcurrentDictionary<GameId, SemaphoreSlim>
// persists across all HTTP requests, serializing concurrent requests per game across threads.
builder.Services.AddSingleton<IGameService, GameService>();
builder.Services.AddSingleton<IScoreboardService, ScoreboardService>();
```

### Lifetime Rationale:
1. `InMemoryGameRepository`: **Singleton** — holds in-memory active game aggregates across requests.
2. `InMemoryScoreboardRepository`: **Singleton** — holds in-memory session scoreboard across requests.
3. `IComputerMoveStrategy`: **Singleton** — stateless pure domain strategy.
4. `IDomainEventDispatcher`: **Singleton** — thread-safe in-process dispatcher.
5. `IGameService`: **Singleton** — holds the `_gameLocks = ConcurrentDictionary<GameId, SemaphoreSlim>` dictionary. If registered as Scoped, each HTTP request would instantiate a new lock dictionary, bypassing per-game synchronization across concurrent requests.
6. `IScoreboardService`: **Singleton** — stateless service delegating to singleton scoreboard repository.

## 9. Concurrency & Event Flow

### 9.1 Request Concurrency Flow
1. HTTP request hits `GamesController.MakeMove`.
2. Controller maps request to `MakeMoveCommand` and invokes `_gameService.MakeMoveAsync`.
3. `GameService` retrieves or creates `SemaphoreSlim(1, 1)` for the specific `GameId`.
4. `SemaphoreSlim.WaitAsync(cancellationToken)` guarantees serial processing for that game.
5. Other requests for different `GameId`s proceed concurrently without waiting.
6. Aggregate mutation, event dispatch, event clearing, and persistence execute.
7. Semaphore released in `finally` block.

### 9.2 GameCompleted Domain Event Flow
1. Move transitions game to `Won` or `Draw`.
2. `Game.MakeMove` raises `GameCompletedEvent` into `_domainEvents`.
3. `GameService` detects pending events.
4. `GameService` dispatches events through `IDomainEventDispatcher`.
5. `GameCompletedEventHandler` loads authoritative `Scoreboard`, calls `RecordGameCompleted`, and saves it.
6. Only after successful dispatch does `GameService` call `game.ClearDomainEvents()`.
7. `GameService` saves `Game` to repository.

## 10. Middleware & Cross-Cutting Architecture

1. **Global Exception Handling**:
   - Implemented via custom middleware `ProblemDetailsMiddleware` or .NET 8 `IExceptionHandler`.
   - Intercepts domain and application exceptions, generates standard RFC 7807 problem details with correct status code, title, and structured code.
   - Logs errors using `ILogger` with correlation IDs.
2. **CORS Configuration**:
   - Existing `FrontendPolicy` in `Program.cs` restricting origins to `http://localhost:4200`.
   - Preflight `OPTIONS` requests handled automatically.
3. **Health Check Endpoint**:
   - `/health` returning `200 OK` (already established in `Program.cs`).
4. **JSON Serialization**:
   - `System.Text.Json` configured with `JsonStringEnumConverter` so `Player`, `GameMode`, and `GameStatus` serialize as clean strings matching the API contract.
   - CamelCase property naming enabled by default.
