## 3. Game Aggregate Boundary Review

The `Game` aggregate root encapsulates the following state:

```text
Game
 ├── Board
 ├── MoveHistory
 ├── CurrentPlayer
 ├── Status
 ├── Winner
 └── WinningCells
```

### Boundary Justification Matrix

| Element | Why it belongs inside Aggregate | Invariant supported | Mutated strictly by |
|---|---|---|---|
| **Board** | Represents the actual 3x3 play surface and cell marks for the game session. | Exactly 9 cells (0..8); cell marks can only be set via legal game moves; occupied cells cannot be overwritten. | Strictly `Game` aggregate via `MakeMove` (or snapshot restore in P006). Callers receive read-only views (`Cells`, `GetCell`). |
| **MoveHistory** | Represents the chronological record of valid moves executed in this game. | Move numbers are contiguous 1-based integers; history matches accepted moves; only legal moves are recorded. | Strictly `Game` aggregate during `MakeMove` (or undo in P006). Exposed as `IReadOnlyList<Move>`. |
| **CurrentPlayer** | Defines which player has the right to play the next move in this game. | Player X starts; only current player may play; turns alternate between X and O upon valid moves. | Strictly `Game` aggregate on valid move acceptance. |
| **Status** | Defines the lifecycle state of the game session (`InProgress`, `Won`, `Draw`). | Moves are accepted ONLY when `Status == InProgress`; terminal games cannot receive moves (`GameAlreadyCompletedException`). | Strictly `Game` aggregate upon move resolution (or reset). |
| **Winner** | Identifies the victorious player (`X`, `O`, or `null`). | `null` while `InProgress` or upon `Draw`; must identify winning player upon `Won`. | Strictly `Game` aggregate upon transition to `Won` (or reset). |
| **WinningCells** | Identifies the exact cell indices forming the winning line for presentation. | Empty array while `InProgress` or `Draw`; exactly 3 cell indices when `Won`. | Strictly `Game` aggregate upon transition to `Won` (or reset). |

## 4. WinningCells / Winner State Analysis

- **P004 Boundary**: Establishes the static **domain state vocabulary** required for the aggregate root's public shape and invariants (e.g. initial game has `Winner == null`, `WinningCells == empty`, `Status == InProgress`, and moves on completed games throw `GameAlreadyCompletedException`).
- **P005 Boundary**: Establishes the **state transition rules** (win detector evaluating rows/columns/diagonals and draw detector evaluating full board).
- **Conclusion**: Retaining `Winner`, `WinningCells`, `GameStatus.Won`, and `GameStatus.Draw` as domain state properties in P004 without implementing win evaluation is architecturally sound and preserves clear separation between vocabulary and transition rules.

## 5. Board.Clone() Review

- **Why it exists**: `Board.Clone()` provides a low-level, defensive deep-copy primitive on the `Board` entity, returning a new `Board` instance initialized with the same cell marks.
- **What guarantees it provides**: Guarantees memory isolation. Mutations to the cloned board cannot affect the original board and vice-versa.
- **Distinction from Memento**: `Board.Clone()` is NOT the Memento pattern. It only duplicates the internal cell array; it possesses no concept of game lifecycle, player turn, move history, or restoration commands.
- **Future use in P006**: When P006 implements `GameMemento`, the `Game` originator will use `Board.Clone()` internally to capture an isolated snapshot of the board without exposing internal mutable array state.
- **Conclusion**: Retain `Board.Clone()`. It is a well-encapsulated internal copy primitive with zero architectural leakage.

## 6. IGameRepository Placement Review

- **Options Considered**:
  - `TicTacToe.Domain.Repositories` (Domain Layer)
  - `TicTacToe.Application.Contracts` (Application Layer)
- **Architectural Analysis**:
  - In Domain-Driven Design (Evans/Vernon) and Onion/Clean Architecture, the aggregate root and its repository abstraction belong together in the Domain layer as part of the domain boundary.
  - The domain defines the persistence contract (`IGameRepository`) for loading and saving the aggregate root.
  - `TicTacToe.Infrastructure` implements the repository (`InMemoryGameRepository`).
  - `TicTacToe.Application` depends on `TicTacToe.Domain` and coordinates domain operations via `IGameRepository`.
  - Dependency inversion is strictly maintained: `Domain` has zero dependencies on any layer, `Application` depends only on `Domain`, and `Infrastructure` implements the domain contract.
- **Specification Evidence**: `docs/04-ddd-and-domain-model.md` §14 and `docs/05-architecture.md` §1, §9.
- **Conclusion**: `IGameRepository` is correctly placed in `TicTacToe.Domain.Repositories`.

## 8. Invariant Tests Review and Corrections

### Correction Details (per Section 12 requirements)
- **Problem**: Negative move test cases in `GameTests.cs` asserted only partial state retention (e.g. checking `MoveHistory` and target cell, but omitting assertions for `Status`, `Winner`, `WinningCells`, and remaining cells). Additionally, `GameAlreadyCompletedException` had no unit test verifying that move attempts on completed games are rejected and preserve aggregate state.
- **Specification Evidence**: `docs/04-ddd-and-domain-model.md` §5 requires that failed operations leave the aggregate state unmutated across all state properties (`Board`, `MoveHistory`, `CurrentPlayer`, `Status`, `Winner`, `WinningCells`). `docs/ai/prompts/P004.1-domain-model-review-and-boundary-verification.md` §8 mandates verifying this exact invariance.
- **Current Behavior**: `MakeMove_WrongPlayer` and `MakeMove_OccupiedCell` checked 3 of 6 state facets. No test verified `GameAlreadyCompletedException`.
- **Required Behavior**: Explicitly assert all 6 aggregate state facets remain intact upon failed moves, and verify `GameAlreadyCompletedException` on terminal states.
- **Correction Applied**:
  1. Updated `MakeMove_WrongPlayer_ThrowsInvalidTurnExceptionAndDoesNotMutateState` to assert all 9 board cells remain null, `MoveHistory` remains empty, `CurrentPlayer` is unchanged, `Status` is `InProgress`, `Winner` is null, and `WinningCells` is empty.
  2. Updated `MakeMove_OccupiedCell_ThrowsCellOccupiedExceptionAndDoesNotMutateState` to assert occupied cell remains intact, other 8 cells remain null, `MoveHistory` count remains 1, `CurrentPlayer` is unchanged, `Status` is `InProgress`, `Winner` is null, and `WinningCells` is empty.
  3. Added `MakeMove_WhenGameAlreadyCompleted_ThrowsGameAlreadyCompletedExceptionAndPreservesState` (xUnit `[Theory]` for `Won` and `Draw`) asserting that attempted moves throw `GameAlreadyCompletedException` with the correct status and leave all aggregate state completely unmutated.
- **Test Evidence**: All 37 backend tests pass (100% success rate).
