1. Executive Summary

This document provides a comprehensive architectural blueprint for the Tic-Tac-Toe Enterprise Solution — a full-stack web application demonstrating disciplined, test-driven, enterprise software engineering. The system features a .NET 8 backend following Domain-Driven Design (DDD) and Onion Architecture principles, paired with an Angular 21 frontend using Standalone Components and reactive Signals.

The application supports Two-Player (pass-and-play) and Computer (human vs AI) game modes, with features including move history tracking, snapshot-based undo, session-level scoreboard, and deterministic computer AI — all governed by the backend as the single source of truth.

Key Metrics: 5 backend projects · 7 Angular components · 238 automated tests · 7 REST endpoints · 3 GoF design patterns · 100% domain rule test coverage

3. System Architecture & Onion Layers

3.1 Onion Architecture

The backend strictly follows Onion (Clean) Architecture with four concentric layers. Dependencies point exclusively inward — outer layers depend on inner layers, never the reverse.

4. Low-Level Design (LLD) — Domain Layer

Domain — Project: TicTacToe.Domain

The Domain layer is the heart of the system. It contains all business rules, game invariants, and domain logic. It has zero dependencies on any external framework, HTTP library, or persistence technology.

4.1 Game Aggregate Root

Aggregates/Game.cs — 227 lines

The Game class is the Aggregate Root — the sole entry point for all game mutations. It is the Originator and Caretaker in the GoF Memento Pattern.

Responsibilities

  • Enforces all game lifecycle invariants (InProgress → Won/Draw)
  • Validates turn alternation (X→O→X→…)
  • Validates move legality (cell bounds, cell vacancy)
  • Delegates win detection to WinDetector domain service
  • Manages Memento snapshots for undo operations
  • Coordinates Computer Mode turns via ExecuteTurn()

Key Methods

MethodSignatureDescription
Createstatic Game Create(GameMode mode)Factory method creating a fresh game with a new GUID
MakeMovevoid MakeMove(Player, CellIndex)Executes a validated player move; captures memento, places mark, checks win/draw, alternates turn
PlayComputerMoveCellIndex PlayComputerMove(IComputerMoveStrategy)Executes Computer (Player O) move using injected strategy
ExecuteTurn(CellIndex, CellIndex?) ExecuteTurn(CellIndex, IComputerMoveStrategy)Orchestrates human X + computer O as a single logical turn
Undovoid Undo()Restores previous state from memento stack
Resetvoid Reset()Clears game state while preserving GameId

Business Invariants Enforced

  1. Game must be InProgress to accept moves
  2. Player must match CurrentPlayer
  3. Target cell must be unoccupied
  4. Memento snapshot captured before every mutation
  5. Win detection evaluated after every move (8 canonical lines)
  6. Draw detected when board is full with no winner
  7. Undo disabled after game completion (Option A — ADR-004)
  8. Computer moves only in Computer mode when it's Player O's turn

Memento Capture Logic

  • TwoPlayer Mode: Captures memento before every move
  • Computer Mode: Captures memento before the human (X) move only — this ensures undo reverts the entire human+computer pair atomically

4.2 Board Entity

Entities/Board.cs — 84 lines

The Board entity represents the 3×3 game grid as a flat 9-cell array indexed 0–8.

Why a Flat Array?

  • Simpler indexing (single cellIndex) vs. row/column pairs
  • Direct alignment with the API contract (cellIndex 0–8)
  • Canonical board layout: 0 1 2 / 3 4 5 / 6 7 8

Key Properties & Methods

4.3 Scoreboard Entity

Entities/Scoreboard.cs — 86 lines

Tracks session-level game outcomes: X wins, O wins, and Draws. Designed as a separate entity (not part of the Game aggregate) to decouple game lifecycle from global session counters.

Thread Safety

Uses internal lock (_syncLock) synchronization on all mutation methods (RecordWin, RecordDraw, Reset) and on TotalGames, ensuring safe concurrent access from multiple game completions.

4.4 Value Objects

Value ObjectFileDescriptionKey Invariant
GameId ValueObjects/GameId.cs Strongly-typed GUID identity for game sessions Cannot be Guid.Empty
CellIndex ValueObjects/CellIndex.cs Canonical board cell index (0–8) 0 ≤ value ≤ 8

Move ValueObjects/Move.cs Immutable record: MoveNumber, Player, CellIndex MoveNumber ≥ 1

Why Value Objects?

  • Self-Validating: Invariants are enforced at construction (e.g., CellIndex rejects values outside 0–8)
  • Primitive Obsession Prevention: Prevents passing raw int / Guid values that could be semantically incorrect
  • Type Safety: Compiler-enforced — cannot accidentally pass a GameId where a CellIndex is expected
  • Immutability: Implemented as readonly record struct for zero-allocation value semantics

4.5 Domain Services

4.5.1 WinDetector

Services/WinDetector.cs — 54 lines

A stateless domain service that evaluates the board against the 8 canonical winning lines (3 rows + 3 columns + 2 diagonals).

private static readonly int[][] WinningLines = {
    new[] { 0, 1, 2 }, // Row 0
    new[] { 3, 4, 5 }, // Row 1
    new[] { 6, 7, 8 }, // Row 2
    new[] { 0, 3, 6 }, // Column 0
    new[] { 1, 4, 7 }, // Column 1
    new[] { 2, 5, 8 }, // Column 2
    new[] { 0, 4, 8 }, // Main diagonal
    new[] { 2, 4, 6 }  // Anti-diagonal
};

Returns a WinResult record containing: IsWin, Winner, and the exact 3 WinningCells indices. Returns WinResult.None if no winner.

4.5.2 IComputerMoveStrategy (Interface)

Services/IComputerMoveStrategy.cs — 25 lines

The Strategy Pattern interface defining the contract for AI move selection. Implementations must be:

  • Pure: No side effects, no mutation of the board or aggregate
  • Deterministic: Same board state always yields the same move
  • Legal: Never returns an occupied cell

4.5.3 BasicComputerMoveStrategy

Services/BasicComputerMoveStrategy.cs — 96 lines

The concrete AI implementation using a 5-tier deterministic priority hierarchy:

PriorityRuleDescription
1WinIf O can complete a winning line, take it (lowest index if multiple)
2BlockIf X can win next turn, block it (lowest threatened index)
3CenterTake center cell (index 4) if available
4CornersTake corners in deterministic order: 0 → 2 → 6 → 8
5FallbackTake the first available cell in natural order 0→8

Implementation Technique: Win/Block detection uses candidate simulation — for each empty cell, a cloned board is created and the candidate move is placed, then WinDetector.CheckWin() evaluates whether it produces a win. This is pure (no mutation of the real board).

4.6 GameMemento

Mementos/GameMemento.cs — 17 lines

An internal sealed record capturing a complete snapshot of the Game aggregate's state for undo operations. Stores:

  • Board snapshot (deep clone)
  • CurrentPlayer
  • GameStatus
  • Winner
  • WinningCells
  • MoveHistory

Visibility is internal — only the Game aggregate (Originator) within the Domain assembly can create or consume mementos. This prevents external layers from accessing or tampering with snapshots.

5. Low-Level Design (LLD) — Application Layer

Application — Project: TicTacToe.Application

The Application layer is the orchestration layer — it coordinates domain objects, manages persistence, and translates domain state into DTOs. It is transport-neutral (no ASP.NET Core dependencies).

5.1 GameService

Services/GameService.cs — 184 lines

Responsibilities

  • Orchestrates Game aggregate lifecycle (create, move, undo, reset)
  • Manages per-GameId concurrency synchronization via ConcurrentDictionary<GameId, SemaphoreSlim>
  • Detects terminal state transitions (InProgress → Won/Draw) and updates the Scoreboard
  • Coordinates Computer Mode logical turns (human X + computer O atomically)
  • Maps aggregate state to DTOs for the API layer

Use Case Methods

MethodDescription
CreateGameAsyncCreates a new Game aggregate, persists it, returns DTO
GetGameAsyncRead-only retrieval of current game state
MakeMoveAsyncValidates and executes a move (+ computer response in Computer mode), detects terminal transition, updates scoreboard, persists, returns DTO
UndoAsyncRestores previous state from memento, persists
ResetGameAsyncResets game while preserving GameId, persists

Concurrency Design

Each GameId gets its own SemaphoreSlim(1,1) mutex, ensuring that concurrent HTTP requests targeting the same game are serialized. This prevents race conditions where two moves could be applied simultaneously.

var lockObj = _gameLocks.GetOrAdd(gameId, _ => new SemaphoreSlim(1, 1));
await lockObj.WaitAsync(cancellationToken);
try {
    // ... atomic game mutation ...
} finally {
    lockObj.Release();
}

Thread-safe in-memory storage using ConcurrentDictionary<GameId, Game>. Implements IGameRepository.

6.2 InMemoryScoreboardRepository

Repositories/InMemoryScoreboardRepository.cs — 39 lines

Holds a single Scoreboard instance for the session lifetime. Thread safety is delegated to the Scoreboard entity's internal locks. SaveScoreboardAsync is a no-op because the in-memory reference is mutated in place.

6.3 Persistence Evolution Path

Current: ConcurrentDictionary (In-Process) ↓ Near-term: SQLite + EF Core ↓ Production: PostgreSQL / SQL Server + Optimistic Concurrency ↓ Scale-out: Distributed Cache (Redis) + Event Sourcing

The Repository Pattern and Dependency Inversion ensure this evolution requires changes only in the Infrastructure project — Domain and Application layers remain untouched.

9. Design Patterns & Rationale

9.1 Memento Pattern (GoF)

Behavioral

RoleImplementationFile
OriginatorGame aggregateAggregates/Game.cs
MementoGameMemento (internal record)Mementos/GameMemento.cs
CaretakerGame._undoStack (Stack<GameMemento>)Aggregates/Game.cs

Why Memento for Undo?

  • Accuracy: Snapshot-based restore guarantees exact previous state — no heuristic reversal bugs
  • Atomicity: In Computer mode, one snapshot captures the state before both human and computer moves — single undo reverts the entire pair
  • Encapsulation: GameMemento is internal — external layers cannot tamper with snapshots
  • Alternative Rejected: Event Sourcing would add unnecessary complexity for a 3×3 board

9.2 Strategy Pattern (GoF)

Behavioral

RoleImplementationFile
Strategy InterfaceIComputerMoveStrategyServices/IComputerMoveStrategy.cs
Concrete StrategyBasicComputerMoveStrategyServices/BasicComputerMoveStrategy.cs
ContextGame.PlayComputerMove()Aggregates/Game.cs

Why Strategy for AI?

  • Open/Closed Principle: New AI algorithms (Minimax, ML-based) can be added by implementing the interface — no modification to Game or GameService
  • Testability: Strategy can be unit-tested independently with mock boards
  • DI-Friendly: Injected via constructor in GameService; swappable at runtime or via configuration

9.3 Repository Pattern

Structural

Why Repository?

  • Dependency Inversion: Domain defines interfaces; Infrastructure provides implementations
  • Persistence Ignorance: Domain and Application layers have zero knowledge of ConcurrentDictionary
  • Swappability: Can swap to EF Core, Dapper, or Redis without touching domain code
  • Testability: Easy to mock repositories for application service tests

9.4 Facade Pattern

Structural

The frontend GameFacade provides a simplified interface over multiple API services and state signals. Components interact with a single facade instead of managing API calls, error handling, and state synchronization individually.

9.5 Factory Method Pattern

Creational

Game.Create(GameMode) is a static factory method ensuring proper initialization of all aggregate state with a fresh GUID and default values.

10.4 API Invariants

  1. Client cannot supply authoritative board state
  2. Client cannot force current player
  3. Client cannot force winner/status
  4. Client cannot mutate scoreboard through game commands
  5. GET has no side effects
  6. cellIndex is the sole cell-addressing contract
  7. Every successful command returns sufficient state for UI rendering

17. Appendix A — SQLite Migration: Architecture & Implementation Changes

This section provides a comprehensive guide on every architecture and implementation change required to replace the current in-memory ConcurrentDictionary storage with SQLite via Entity Framework Core. Because the system was designed with the Repository Pattern and Dependency Inversion, the Domain and Application layers remain completely untouched — changes are isolated to Infrastructure and the API composition root.

Key Principle: The existing IGameRepository and IScoreboardRepository interfaces in the Domain layer act as the seam. We implement new classes behind these interfaces — the Domain, Application, and Frontend layers require zero modifications.

17.5.2 DbContext

[NEW] Persistence/TicTacToeDbContext.cs

namespace TicTacToe.Infrastructure.Persistence;

using Microsoft.EntityFrameworkCore;
using TicTacToe.Infrastructure.Persistence.Entities;

public class TicTacToeDbContext : DbContext
{
    public DbSet<GameEntity> Games => Set<GameEntity>();
    public DbSet<MoveEntity> Moves => Set<MoveEntity>();
    public DbSet<ScoreboardEntity> Scoreboards => Set<ScoreboardEntity>();

    public TicTacToeDbContext(DbContextOptions<TicTacToeDbContext> options)
        : base(options) { }

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        // Game entity configuration
        modelBuilder.Entity<GameEntity>(entity =>
        {
            entity.HasKey(e => e.Id);
            entity.Property(e => e.Id).ValueGeneratedNever();
            entity.Property(e => e.Version).IsConcurrencyToken();
            entity.Property(e => e.Board).IsRequired();
            entity.Property(e => e.UndoStack).IsRequired();
            entity.Property(e => e.WinningCells).IsRequired();
            entity.HasMany(e => e.Moves)
                  .WithOne(m => m.Game)
                  .HasForeignKey(m => m.GameId)
                  .OnDelete(DeleteBehavior.Cascade);
        });

        // Move entity configuration
        modelBuilder.Entity<MoveEntity>(entity =>
        {
            entity.HasKey(e => e.Id);
            entity.HasIndex(e => new { e.GameId, e.MoveNumber }).IsUnique();
        });

        // Scoreboard entity configuration (singleton row)
        modelBuilder.Entity<ScoreboardEntity>(entity =>
        {
            entity.HasKey(e => e.Id);
            entity.Property(e => e.Version).IsConcurrencyToken();
            // Seed the singleton row
            entity.HasData(new ScoreboardEntity
            {
                Id = 1, XWins = 0, OWins = 0, Draws = 0, Version = 0
            });
        });
    }
}

17.5.3 SqliteGameRepository

[NEW] Repositories/SqliteGameRepository.cs

This is the most complex new file. It must:

  1. Hydrate (Load): Read GameEntity + MoveEntity rows from SQLite → reconstruct the domain Game aggregate with full internal state (board, history, undo stack)
  2. Dehydrate (Save): Decompose the domain Game aggregate → flatten into GameEntity + MoveEntity rows → persist via EF Core
  3. Handle Concurrency: Use the Version column as an optimistic concurrency token
namespace TicTacToe.Infrastructure.Repositories;

public sealed class SqliteGameRepository : IGameRepository
{
    private readonly TicTacToeDbContext _db;

    public SqliteGameRepository(TicTacToeDbContext db)
    {
        _db = db ?? throw new ArgumentNullException(nameof(db));
    }

    public async Task<Game?> GetByIdAsync(
        GameId gameId, CancellationToken ct = default)
    {
        var entity = await _db.Games
            .Include(g => g.Moves.OrderBy(m => m.MoveNumber))
            .FirstOrDefaultAsync(g => g.Id == gameId.Value, ct);

        if (entity == null) return null;

        return ReconstructAggregate(entity);
    }

    public async Task SaveAsync(
        Game game, CancellationToken ct = default)
    {
        var existing = await _db.Games
            .Include(g => g.Moves)
            .FirstOrDefaultAsync(g => g.Id == game.Id.Value, ct);

        if (existing == null)
        {
            var entity = DehydrateToEntity(game);
            entity.CreatedAt = DateTime.UtcNow;
            entity.UpdatedAt = DateTime.UtcNow;
            _db.Games.Add(entity);
        }
        else
        {
            UpdateEntity(existing, game);
            existing.UpdatedAt = DateTime.UtcNow;
            existing.Version++;  // Bump concurrency token
        }

        await _db.SaveChangesAsync(ct);
    }

    // --- Private mapping methods ---
    // ReconstructAggregate(): Entity → Domain Aggregate
    // DehydrateToEntity():   Domain Aggregate → Entity
    // UpdateEntity():        Sync entity from aggregate
}

17.5.4 Aggregate Reconstitution Challenge

The Hardest Part: The current Game aggregate has a private constructor and private fields (_undoStack, _moveHistory). Reconstituting it from a database row requires one of these approaches:
ApproachProsConsRecommendation
A. Internal reconstitution constructor Clean, explicit, preserves encapsulation Adds an internal constructor to Game ✅ Recommended
B. Reflection-based hydration No domain changes Fragile, breaks on rename, hard to debug ❌ Avoid
C. Replay moves from history No domain changes O(n) per load, doesn't restore undo stack ❌ Inadequate
D. Builder/Hydrator in Domain Clean separation More complex than needed ⚠️ Over-engineered

Recommended: Internal Reconstitution Constructor

Add one new internal constructor to the Game class (the only domain change):

// Add to Game.cs — internal constructor for persistence reconstitution
internal Game(
    GameId id,
    GameMode mode,
    GameStatus status,
    Player currentPlayer,
    Player? winner,
    IReadOnlyList<int> winningCells,
    Board board,
    List<Move> moveHistory,
    Stack<GameMemento> undoStack)
{
    Id = id;
    Mode = mode;
    Status = status;
    CurrentPlayer = currentPlayer;
    Winner = winner;
    WinningCells = winningCells;
    Board = board;
    _moveHistory = moveHistory;
    _undoStack = undoStack;
}
Visibility: The constructor is internal, so only the Infrastructure project (which has InternalsVisibleTo) can call it. External consumers and the API layer cannot bypass the normal Game.Create() factory.

17.5.5 SqliteScoreboardRepository

[NEW] Repositories/SqliteScoreboardRepository.cs

namespace TicTacToe.Infrastructure.Repositories;

public sealed class SqliteScoreboardRepository : IScoreboardRepository
{
    private readonly TicTacToeDbContext _db;

    public SqliteScoreboardRepository(TicTacToeDbContext db)
    {
        _db = db ?? throw new ArgumentNullException(nameof(db));
    }

    public async Task<Scoreboard> GetScoreboardAsync()
    {
        var entity = await _db.Scoreboards.FindAsync(1);
        if (entity == null)
        {
            return new Scoreboard();
        }
        return new Scoreboard(entity.XWins, entity.OWins, entity.Draws);
    }

    public async Task SaveScoreboardAsync(Scoreboard scoreboard)
    {
        var entity = await _db.Scoreboards.FindAsync(1);
        if (entity == null)
        {
            entity = new ScoreboardEntity { Id = 1 };
            _db.Scoreboards.Add(entity);
        }
        entity.XWins = scoreboard.XWins;
        entity.OWins = scoreboard.OWins;
        entity.Draws = scoreboard.Draws;
        entity.Version++;
        await _db.SaveChangesAsync();
    }
}

ServiceBefore (In-Memory)After (SQLite)Why Changed
IGameRepositorySingletonScopedDbContext is Scoped (one per HTTP request); repository must match

Important — GameService Lock Migration: The current GameService uses a ConcurrentDictionary<GameId, SemaphoreSlim> for per-game locking. When changing to Scoped lifetime, this in-memory lock dictionary is recreated per request and no longer works. Two options:
  1. Extract locks to a Singleton service: Create an IGameLockProvider registered as Singleton that holds the lock dictionary
  2. Rely on database optimistic concurrency: Remove in-process locks entirely; let EF Core's concurrency token (Version column) detect conflicts and throw DbUpdateConcurrencyException, which the middleware maps to 409 Conflict
